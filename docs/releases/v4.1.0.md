# v4.1.0

v4.1.0 changes what `bear plan` and `bear apply` print. Deployment behaviour,
environment policy, source safety, and state publication are unchanged; see the
[v4.0.0 release notes](v4.0.0.md) and the
[v4 migration guide](../migration-v4.md) for those rules.

## Shared Headers And Closing Sentences

`bear plan` now opens with a `Bear Plan` branding header, matching the `Bear Apply`
header, and the `━━━ … ━━━` phase banners are gone. A phase is a plain bold
heading such as `Validating 4 artifacts` or `Deploying 2 artifacts to prd`, so both
halves of a workflow read as one column of text instead of competing rules. The
separate `━━━ Plan ━━━` phase that introduced the summary is gone with them.

Each command also ends with one sentence instead of a symbol line:

```text
Validation complete: 4 artifacts in 3s
Plan complete: 4 validated, 2 to deploy, 1 skipped
Apply complete: 2 deployed, 1 skipped in 15s
Apply failed: 0 deployed, 2 failed, 1 skipped in 11s
```

This replaces `✓ 2 validated  ~ 1 to deploy  – 1 skipped` and
`✓ 1 deployed  ✗ 1 failed  – 1 skipped  total 38.4s`, so a CI log can be read from
the bottom up. Validated, to-deploy, and deployed counts are always reported;
failed and skipped counts appear only when there are any. Plan's closing hint,
`Run 'bear apply' to execute this plan.`, is no longer indented.

## Terraform-Style Progress Without a Terminal

Jenkins, GitLab, and GitHub Actions logs no longer receive a redrawn ASCII
progress bar or the `name | status | phase … | total …` table. Bear now appends
one plain line per job on every status change:

```text
Bear Apply
──────────

Deploying 2 artifacts to prd

  checkout-api:       Deploying...
  checkout-api:       Deploying... [1/3 Build image]
  checkout-api:       Still deploying... [10s elapsed, 1/3 Build image] (1 job queued)
  checkout-api:       Deploying... [2/3 Push image]
  checkout-api:       Deploying... [3/3 Deploy revision]
  checkout-api:       Deployment complete after 15s
  kira-teams-adapter: Deploying...
  kira-teams-adapter: Deploying... [1/3 Build image]
  kira-teams-adapter: Deploying... [2/3 Push image]
  kira-teams-adapter: Deployment failed after 11s: Push image: exit status 1
    denied-missing-registry-credentials
```

- Job names are padded to a common width, so the status text of every line starts in the same column.
- Each running job repeats a `Still …` line every 10 seconds with its total elapsed time and current step, so a silent long-running command never looks hung.
- Jobs waiting for a `--concurrency` slot are appended to the last running job's heartbeat as `(1 job queued)` or `(2 jobs queued)`; the backlog no longer takes a line of its own. The run above used `--concurrency 1`; the default for plan and apply is `10`.
- Jobs finish with `Deployment complete after 15s` or `Deployment failed after 11s: <error>`, followed by the bounded output tail indented four spaces under that job's line.
- Apply's phase heading names its destination, `Deploying 2 artifacts to prd`, so the environment is stated once beside the work.
- Plan validation uses `Validating` / `Still validating` / `Validation complete` / `Validation failed`; `bear check` uses `Checking` / `Still checking` / `Check complete` / `Check failed`.
- Interactive terminals keep the animated progress bar and per-task spinner. Their per-task lines now carry the same `<n>/<total> <step>` labels as the plain output, and an apply task is named by its artifact alone instead of `<artifact> -> <target>`. `--verbose` still streams subprocess output as `  <artifact> | <step> | <line>` and still retains bounded failure diagnostics; it selects the plain, line-per-status display even on a terminal.

See [Live Output](../ci-cd.md#live-output) for the full CI description.

## A Plan Summary You Can Actually Review

`bear plan` closes with a rule, an aligned fact block, counted sections, and its
sentence:

```text
────────────────────────────────────────
Environment: prd
Commit:      b11f03a

deploy (2):
  - checkout-api (services/checkout-api): new artifact
  - kira-teams-adapter (services/kira/teams-adapter): new artifact

skip (1):
  - kira-mail-adapter (services/kira/mail-adapter): deployment not enabled for environment prd

Plan complete: 4 validated, 2 to deploy, 1 skipped
```

The rule is followed by an aligned fact block: `Environment:` always, `Commit:`
with the short source commit — `Pinned:` instead for a pinned plan — plus
`Artifacts:` when artifact filters were given and `Changes:` with the number of
changed files. This replaces the old `Artifacts: …`, `📌 Pinning to: …`, and
`N file(s) changed` lines. Every entry in a plan is built from the same source, so
the commit is reported once in the header rather than under each artifact.

Sections are labelled with their outcome and entry count — `deploy (2):` and
`skip (1):` for plan, `failed (2):` for apply — replacing the old `To Deploy:` and
`Skipped:` headings. Entries are sorted by name, so repeated runs of the same plan
produce comparable summaries even though jobs finish in a nondeterministic order.

**Each artifact is now one line:** `  - <name> (<path>): <reason>`. This replaces
v4.0.0's per-artifact block of `~ <name>` followed by indented `Path:`, `Target:`,
`Reason:`, `Last:`, and `Steps:` detail lines, plus one dimmed line per configured
step — at least six lines per deployment, and more for a multi-step target.
Nothing needed for review was lost: the commit is identical for every entry and is
stated once in the header, and an artifact's target and steps are declared in
`bear.artifact.yml` and `bear.config.yml`, where they can be read and diffed. The
path is omitted when the plan recorded none, and empty sections are omitted.

## Apply Reports Actions, Not the Plan

The plan is the review artifact; apply is the execution log. `bear apply` does not
restate the plan it was handed. A successful run is the phase heading, the job
lines, and the closing sentence — no rule, no `Environment:` block, no `deploy (`
or `skip (` section:

```text
Bear Apply
──────────

Deploying 2 artifacts to prd

  checkout-api:       Deploying...
  checkout-api:       Deploying... [1/3 Build image]
  kira-teams-adapter: Deploying...
  kira-teams-adapter: Deploying... [1/3 Build image]
  checkout-api:       Still deploying... [10s elapsed, 1/3 Build image]
  checkout-api:       Deployment complete after 15s
  kira-teams-adapter: Deployment complete after 15s

Apply complete: 2 deployed, 1 skipped in 15s
```

The environment moved into the phase heading — `Deploying 2 artifacts to prd` —
so it is stated once, beside the work, instead of in a recap. A summary block is
printed only when something failed, and then it contains only the failures:

```text
────────────────────────────────────────
Environment: prd

failed (2):
  - checkout-api (services/checkout-api): Push image: exit status 1
  - kira-teams-adapter (services/kira/teams-adapter): Push image: exit status 1

Apply failed: 0 deployed, 2 failed, 1 skipped in 11s
```

Repeating an approved deploy/skip list here would tell a reader nothing they had
not already approved, while pushing the one thing a deployment log exists for —
what broke — further from the end of a CI log. Keeping the block failure-only means
its presence is itself the signal.

Artifacts checkpointed by an earlier run are not listed anywhere: they are not
redeployed, and they raise only the `skipped` count. `bear.lock.yml` and the
retained plan remain the record of what is deployed. An empty plan now prints
exactly one line, `Plan for prd contains no artifacts to deploy.`, in place of
v4.0.0's `Environment:` line, per-skip `Skipped <name>: <reason>` lines, and
`Plan contains no artifacts to deploy.`

See [plan output](../commands/plan.md#output) and
[apply output](../commands/apply.md#output).

## Plan File Field Addition

`.bear/plan.yml` skip entries now record an optional `path` alongside `name` and
`reason`, so plan can print `checkout-api (services/checkout-api)` for a skip
without re-deriving it. That is the only added field: skips do not store a `target`
or a `commit`, and nothing in the saved plan keeps a per-skip deployment history.
No configuration change is required, and plans written by v4.0.0 stay readable —
their skip entries simply render without a path.

Plans are still written with mode `0600` and can contain secrets; keep copies and
CI artifacts private.

## Operational Limits

Console output is not an audit record. Failure tails are bounded and never
redacted, `--verbose` streams whatever the configured step writes, and the summary
reports Bear's own state rather than the external service's. Reconciliation rules
after a crash, checkpoint failure, or failed Git push are unchanged; see
[source safety and retries](../concepts/plan-apply.md#retries) and
[Git publication](../commands/apply.md#git-publication).
